# Arrodes 首个真实验收：Arduino 外接 LED

> 顺序调整：本验收保留为摄像头能力的第二阶段真实验收。第一阶段先完成电脑屏幕识别与 Arduino IDE 屏幕场景验证。

## 验收目的

证明 Arrodes 不只是描述图片或朗读教程，而是能跨摄像头和屏幕维持任务状态：观察当前证据、只给一个下一步、等待用户完成、验证后再推进，并在证据不足时停止猜测。

## 前置盘点

在冻结接线图前，通过用户提供的套件照片确认：

- Arduino 开发板型号；
- 面包板；
- 普通 LED；
- 标有 220Ω 或 330Ω 的电阻；
- 公对公跳线；
- 可传输数据的 USB 线；
- 可固定并看清面包板孔位的摄像头；
- Arduino IDE 或兼容上传工具。

若套件缺少其中一项，不擅自替换电路或建议带电试错；调整验收任务后再开始。

## 安全边界

- 只使用 Arduino USB/低压逻辑电源，不接市电、外部高压电源、电机或大电流负载。
- 所有插线步骤默认断开 USB；视觉确认拓扑后才允许通电。
- LED 必须串联限流电阻。首轮可依据包装标签或用户确认阻值，不要求视觉模型独立读取细小色环。
- Arrodes 不自动控制硬件，不代替用户插线。
- 看不清孔位、极性或连接关系时必须请求近景或换角度。

## 推荐电路

具体引脚在开发板型号确认后冻结。默认候选为数字引脚 8 → 220Ω/330Ω 电阻 → LED → GND，并使用约 1 秒亮、1 秒灭的程序，便于摄像头观察周期变化。

## 验收流程

1. 用户显式开始“Arduino LED”陪伴任务，并授权摄像头和屏幕观察。
2. Arrodes 根据套件全景建立组件清单；不确定的组件要求用户单独近拍。
3. Arrodes 要求断开 USB，并验证开发板处于未供电状态。
4. 每次只指导放置一个组件或一根线，并给出本步预期的视觉证据。
5. 每次画面变化后重新观察；只有证据满足才进入下一步。
6. 在通电前完成一次整体拓扑检查。至少执行一次无电的安全错误注入，例如故意把一根跳线插到相邻错误行；系统应拒绝继续并指出需要复查的位置。
7. 拓扑通过后连接 USB，切换到屏幕观察，指导选择开发板与端口、编译并上传程序。
8. 系统根据 IDE 状态判断上传成功或失败，不把按钮点击本身当成成功证据。
9. 切回摄像头，通过多个时间点确认 LED 周期闪烁，而不是依据单帧亮灯宣告完成。
10. 用户结束任务后，仅保存任务结果、遇到的问题和必要偏好，不保存原始摄像头或屏幕录像。

## 必须记录的任务状态

- `goal`：完成 Arduino 外接 LED 周期闪烁；
- `currentStep`：当前唯一允许推进的步骤；
- `expectedEvidence`：完成本步必须观察到的对象与关系；
- `observation`：带来源、时间和置信度的摄像头或屏幕证据；
- `decision`：通过、未通过或需要补充画面；
- `nextAction`：用户下一项动作或系统的观察请求；
- `safetyState`：未供电、待检查、允许通电或必须停止。

## 通过标准

- 除开始任务、授权和必要的不确定性确认外，用户不需要用文字持续报告当前步骤。
- 系统不跳步，不在相同画面上重复推进。
- 错误插线或证据不足时不会允许通电。
- 能识别 IDE 的真实编译/上传结果，包括至少一种失败状态。
- 使用时序证据确认 LED 闪烁，不能只确认某一帧为亮。
- 任务中断后能从已验证步骤恢复。
- 完成后生成可诊断日志，能够追踪每次观察为何导致推进或停止。

## 失败与停止条件

出现以下任一情况，不能宣称真实验收通过：

- 用户需要持续用文字告诉系统“我已经做完”；
- 系统在孔位或接线关系不清楚时猜测；
- 错误接线未被拦截便建议通电；
- 仅凭代码已生成或上传按钮已点击就判断成功；
- 仅凭一张 LED 亮起照片判断闪烁；
- 无法解释任务为何推进、退回或停止。

如果在固定机位、固定光照和限定电路下仍无法稳定验证步骤，则暂停现实装配扩展，先解决观察证据和任务状态机制，不增加新的模型、Agent 或场景。

## 首轮明确不验证

- 人脸身份识别；
- 自主焊接指导；
- 通用机器人制作知识；
- 全天候无提示监视；
- 语音和视觉大模型同时 GPU 常驻；
- 自动操作 Arduino 硬件；
- 仅凭视觉判断任意电阻精确阻值。
