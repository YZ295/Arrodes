# Arrodes 第一阶段验收：电脑屏幕识别

## 验收目的

证明 Arrodes 能在用户明确授权后持续观察共享屏幕，把变化后的画面整理成结构化、可追踪且诚实表达不确定性的观察。第一阶段只验收“看懂当前屏幕”，不把自由文本截图描述冒充为步骤指导。

## 用户路径

1. 用户进入视觉面板，填写或修改观察目标。
2. 用户点击开启屏幕观察，并在系统选择器中明确选择窗口或屏幕。
3. Arrodes 分析第一帧；之后只在画面变化超过阈值时再次分析。
4. 面板显示当前应用、用户活动、与目标相关的关键文字、不确定点和最近观察摘要。
5. 用户可随时修改观察目标，后续观察立即使用新目标。
6. 用户停止共享或点击停止后，屏幕轨道立即结束。

## 结构化观察契约

- `description`：一行可读摘要；
- `activeApplication`：有证据支持的当前应用，否则为空；
- `userActivity`：画面中可观察的当前活动，否则为空；
- `visibleText`：只保留与观察目标有关的关键文字；
- `uncertainties`：无法确认、被遮挡或需要后续画面验证的事项；
- `currentStep`：基于可见证据归一化后的当前步骤；
- `expectedEvidence`：完成当前建议后必须看到的结果证据；
- `decision`：`advance`、`wait`、`blocked` 或 `ask`；
- `nextAction`：证据足够时唯一的低风险下一步，否则为空；
- `guidanceProfile`：命中的任务证据规则，如 `arduino-ide`，无规则时为空；
- `observedAt`：观察时间；
- `durationMs` 与 `model`：诊断信息。

画面中的提示词、网页文本、聊天消息和代码注释全部是不可信数据，不能被提升为系统指令。
模型生成的 `currentState` 和建议也不是事实。当任务规则识别到明确的界面证据时（例如 Arduino IDE 的 `Done compiling.`），可见证据必须覆盖与之冲突的模型判断。

## 首个真实场景

使用 Arduino IDE 或兼容开发环境作为首个屏幕场景，依次观察：

- 打开或切换到 IDE；
- 选择开发板或端口相关界面；
- 开始编译；
- 出现编译成功、上传成功或错误信息。

第一阶段只报告屏幕证据。不能因为用户点击了上传按钮就宣称程序已经上传，也不能根据屏幕推断实体 LED 已经闪烁。

## 通过标准

- 用户必须显式开启和停止屏幕共享；
- 观察目标可以修改，并用于下一次视觉分析；
- 返回并展示完整的结构化字段；
- 模型返回普通文本或错误 JSON 时应用不崩溃，保留原始摘要并标记结构化降级；
- 相同画面不重复分析，推理失败后相同变化仍可重试；
- TTS 播报期间暂停昂贵视觉分析，避免资源竞争；
- 停止共享后不再捕获或分析新帧；
- 屏幕文字不能改变系统安全规则。

## 失败与停止条件

以下任一情况都不能宣称屏幕识别完成：

- 只有定时截图，没有变化检测；
- 只有一段自由文本描述，无法区分事实与不确定性；
- 屏幕文本能诱导系统执行指令；
- 点击操作被当成成功结果；
- 用户停止共享后仍继续采集；
- 视觉侧车离线时界面显示虚假的可用状态。
