# Pi Agent 深度研究与阿罗德斯采用建议

研究日期：2026-09-13  
研究对象：Earendil Works / Mario Zechner 的 Pi Agent Harness（原 `badlogic/pi-mono`，现 `earendil-works/pi`）  
核对版本：`0.85.1`，源码提交 `71dca871bc80b6bc97be37f0ca3189399d651fff`

## 用户关注的核心结论

Pi 对阿罗德斯当前开发阶段最值得学习的是**能力增长顺序**：

```text
最小任务流程 → 实际执行 → 找到具体失败点
→ 判断缺少提示、工具、skill，还是流程本身有问题
→ 只补足这个缺口 → 重新执行并验证
```

不应先收集大量 skill，再试图用它们拼出一个“全能智能体”。skill 数量不会自动形成可靠能力，反而会增加选择冲突、上下文消耗、权限面积和维护成本。阿罗德斯现阶段应先证明最小闭环能稳定运行；只有任务已经走到某一步，并且明确因为缺少一项专业方法而失败时，才添加对应 skill。

这意味着近期重点不是接入 Pi。Pi 可以继续作为实现方式的参考，但不进入当前开发主线。

## 架构层面的次要结论

Pi 最值得阿罗德斯学习的不是界面，也不是把 Pi 整体嵌入产品，而是四个稳定边界：

1. **模型层与 agent loop 分离**：模型供应商只负责流式生成，agent loop 只负责消息、工具调用、转向与结束条件。
2. **运行态消息与模型上下文分离**：应用可以保存观察、通知、UI 状态等自定义消息，只有经过 `transformContext` 和 `convertToLlm` 后的内容才进入模型。
3. **所有执行产生统一事件**：开始、增量、结束、工具调用、工具结果都形成稳定事件流，界面与日志不必猜后端状态。
4. **会话是可分支的事件历史**：JSONL 记录通过 `id/parentId` 形成树，压缩只改变送入模型的上下文，不销毁原始历史。

阿罗德斯不应采用 Pi 的默认安全口径。Pi 明确没有内置沙箱和默认权限弹窗，进程拥有启动用户的权限；这适合开发者主动监督的编码工具，不适合持续感知、可能代办桌面动作的个人管家。阿罗德斯必须继续保留自己的 ActionGate、显式授权、可撤销策略、审计记录和结果验证。

如果未来确有替换执行器的需求，Pi 可以作为候选执行内核，与 DSH、Codex SDK 并列放在执行适配层后面；目前不做接入。Pi 不应成为阿罗德斯的产品内核、权威记忆库或权限中心。

## Pi 到底是什么

Pi 目前是一个 TypeScript monorepo，不再只是早期的极简 CLI。主要层次是：

| 层 | 包 | 责任 |
|---|---|---|
| 模型适配 | `pi-ai` | 多供应商模型、流式输出、工具调用、用量与思考档位 |
| Agent 核心 | `pi-agent-core` | 有状态 agent loop、工具执行、事件、steer/follow-up、上下文转换 |
| 编码产品层 | `pi-coding-agent` | 会话、压缩、资源加载、扩展、技能、TUI、RPC、项目可信决策 |
| 展现层 | `pi-tui` | 终端 UI |
| 组合/协议 | `chord`、`protocol`、`client`、`server` | 服务组合、RPC/远程客户端能力 |
| 会话后端 | `session-backends/*` | 可替换的持久化实现，包括 SQLite |

在所核对提交中，`agent`、`ai`、`coding-agent` 三部分共有约 529 个 TypeScript 文件、10.8 万行。这说明“核心保持小”主要是设计哲学，不等于整个项目很小。真正薄的是最基础的 `Agent`/`agentLoop` 使用面；完整 coding harness 已经是一套成熟系统。

## 运行循环

Pi 的单轮结构可以概括为：

```text
用户消息
  → transformContext（裁剪、压缩、注入外部上下文）
  → convertToLlm（过滤 UI/应用专用消息）
  → 模型流式响应
  → 校验工具参数
  → beforeToolCall（可阻止）
  → 执行工具（默认同批并行，可强制顺序）
  → afterToolCall（审计或改写结果）
  → 工具结果进入下一次模型调用
  → 无工具调用后结束，或处理 steer/follow-up 队列
```

其优点是每个阶段都有明确职责。尤其值得借鉴的是：

- `beforeToolCall` 在参数校验后、真实副作用前运行；
- `afterToolCall` 在结果进入事件流和上下文前运行；
- 同一批工具可并行，但带文件副作用的工具可以强制顺序；
- 用户在运行中发送的 `steer` 会在当前工具批完成后改变下一轮方向；
- `followUp` 只在当前任务自然结束后继续；
- `AbortSignal` 贯穿模型与工具执行。

对阿罗德斯而言，`steer` 很适合管家的“停一下”“不是这个”“先看这里”；但桌面高风险动作不能等当前工具批全部完成，应由 ActionGate 和可取消执行器在更底层立即阻断。

## 上下文与记忆

Pi 把三件经常混在一起的东西分开了：

- **会话历史**：完整事件与消息记录；
- **模型上下文**：当前这次调用实际送入模型的内容；
- **长期记忆**：Pi 核心没有替产品定义权威长期记忆体系。

这正好支持阿罗德斯当前的精简方向：

- SQLite 保存任务、观察、事件、状态与索引；
- Obsidian 保存经用户确认的长期记忆；
- `transformContext` 只在每次推理前召回已确认记忆、当前目标和必要观察；
- `convertToLlm` 丢弃桌宠动画、连接状态、调试通知等不应消耗上下文的消息；
- 上下文压缩是会话技术，不得自动变成长期记忆。

Pi 的树形会话记录也值得采用：分支不复制完整会话，回退和替代方案仍可追踪。但阿罗德斯无需照搬其 JSONL 存储；可以在现有 SQLite 中用 `eventId/parentEventId` 表达同一语义。

## 扩展系统

Pi 扩展可以注册工具、命令、事件处理器和自定义 UI，也能在工具执行前阻止调用。技能、提示模板、主题和扩展可以打包分发。这套机制很灵活，但扩展是同进程 TypeScript，拥有与 Pi 相同的系统权限。

阿罗德斯只应借用其**资源描述方式和生命周期事件**，不能照搬同进程全权限插件模型。更适合的边界是：

- 技能：纯说明和元数据，可按需注入；
- 工具适配器：进程内，但只能调用阿罗德斯受控能力接口；
- 外部执行器：DSH、Codex、Pi 走子进程/RPC，使用限定工作目录和凭据；
- 第三方扩展：默认隔离进程，声明权限后才获得文件、网络、屏幕或执行能力。

## 安全模型差异

Pi 的 project trust 只决定是否加载项目内的设置、扩展和包。官方文档明确说明它不是沙箱，也不会限制模型启动后的工具行为。Pi 默认四个工具可读、写、编辑文件并执行 shell；官方建议用容器、VM 或系统级沙箱隔离不可信任务。

阿罗德斯的威胁模型更严格：它会处理屏幕文字、网页内容、语音和长期记忆，这些都可能包含提示注入或错误指令。因此必须在模型之外保持以下硬边界：

1. 观察数据永远标记为不可信证据，不得直接成为系统指令；
2. 权限由阿罗德斯计算，模型和外部执行器只能提出动作；
3. 文件、桌面、网络与消息发送分别授权；
4. 高风险动作展示目标、影响和可撤销性；
5. 动作完成后由独立证据验证，不能只相信工具返回“成功”；
6. Pi package 或 extension 不得直接进入管家主进程。

## 与当前阿罗德斯的差距

| 能力 | Pi | 当前阿罗德斯 | 建议 |
|---|---|---|---|
| Agent loop | 单一、清晰、事件完整 | WebSocket、LLM、技能调用、确认逻辑分散 | 收敛为一个运行时状态机 |
| 事件协议 | 稳定的 agent/turn/message/tool 生命周期 | 有 WS 事件，但产品事件和模型事件混合 | 建立统一 `RuntimeEvent` |
| 运行中转向 | steer、follow-up、abort 语义明确 | 主要有 cancel，后续指令语义较弱 | 增加 steer/follow-up 队列 |
| 上下文转换 | 两阶段明确分离 | 记忆注入、消息历史和画像仍有多条路径 | 建立唯一 ContextBuilder |
| 会话分支 | 原生树结构与分支摘要 | 更偏线性会话 | 后续任务回退时再引入父事件 |
| 模型适配 | 多供应商统一且成熟 | 自有 LLM provider + Codex/WorkBuddy adapters | 不重复扩张；执行层可试用 Pi RPC |
| 权限 | 默认无权限弹窗、无内置沙箱 | 已有 ActionGate 与确认 | 保留阿罗德斯实现 |
| 长期记忆 | 不替产品做权威记忆 | 正在收敛 SQLite + Obsidian | 继续由阿罗德斯掌握 |
| 感知闭环 | 非产品主线 | 屏幕观察、管家、控制台是核心 | 不能交给 Pi |

## 阿罗德斯当前应采用的最小开发顺序

第一条可验收流程只保留：

```text
用户开始屏幕陪伴任务 → 控制台取得结构化观察
→ 阿罗德斯给出一个下一步 → 管家显示这一步
→ 等待屏幕变化 → 判断完成、失败或证据不足
```

这条流程跑通以前，暂停扩张新 skill 市场、大量预装 skill、多 Agent 研讨会、复杂编排、新模型供应商、自我修改、长期自治主循环，以及 Pi/DSH/Codex 多执行器同时接入。

每项新增能力必须回答：当前流程具体卡在哪一步；这是缺少 skill，还是观察、状态、工具、权限或验证机制有问题；加入后用哪个真实任务证明它解决了问题。不能回答就暂不添加。能用固定规则或普通代码解决的问题，也不包装成 skill。

## 未来可能的技术落地顺序

### 第一阶段：只学协议，不引入依赖

先在阿罗德斯内部定义统一的 `RuntimeEvent`：`run.started`、`turn.started`、`message.delta`、`tool.requested`、`tool.blocked`、`tool.progress`、`tool.completed`、`turn.completed`、`run.completed`、`run.failed`。让 Agent 主界面、控制台、管家和审计日志消费同一事件，而不是各自解释状态。

同时建立唯一 `ContextBuilder`，输入是目标、任务状态、最近会话、已确认记忆、结构化观察；输出是送给模型的消息。候选记忆、原始屏幕文本和 UI 状态默认不进入系统指令。

### 第二阶段：仅在真实任务需要时评估 Pi RPC

把 Pi 当作与 DSH、Codex SDK 同级的 `ExecutionBackend`，只验证一个限定目录编码任务：

- 独立子进程；
- `--mode rpc`；
- 独立 session 目录；
- 只开放指定工作区；
- 所有 tool event 映射成阿罗德斯 `RuntimeEvent`；
- 写操作仍经过阿罗德斯授权；
- 完成后返回结构化结果、变更摘要、验证证据。

成功标准不是“Pi 能写代码”，而是阿罗德斯可以在不改变 UI、记忆和权限模型的情况下替换 Pi/DSH/Codex 三种执行器。

### 第三阶段：再决定是否复用 SDK

只有当 RPC POC 证明进程管理和事件转换成本明显高于 SDK 集成，才考虑直接使用 `@earendil-works/pi-agent-core`。即便采用 SDK，也只复用 loop、事件和上下文钩子；不要引入完整 TUI、全局配置、Pi package 管理或 Pi 的权限口径。

## 明确不建议做的事

- 不把阿罗德斯做成 Pi extension；这会让产品内核依赖一个编码工具的生命周期和权限模型。
- 不用 Pi session 代替阿罗德斯长期记忆；会话压缩与长期记忆是不同问题。
- 不同时长期维护阿罗德斯自有完整 agent loop、DSH loop、Pi loop 三套相同能力；阿罗德斯应统一协议，把 loop 视为可替换执行实现。
- 不开放任意 Pi packages 给普通用户直接安装；同进程全权限与私人管家的感知数据不相容。
- 不因为 Pi 支持很多模型，就继续在主界面堆模型入口；模型选择属于运行配置，用户主要关心任务结果和权限。

## 对产品方向的修正

Pi 进一步证明：阿罗德斯的竞争力不应是“再造一个更大的通用 Agent”。成熟执行器已经具备模型路由、工具循环、上下文压缩、分支会话和扩展。阿罗德斯应把研发资源集中在这些执行器没有替用户解决的部分：持续但透明的感知、一步指导、证据验证、跨任务长期记忆、细粒度授权，以及管家与控制台之间清楚的状态呈现。

因此，Pi 对阿罗德斯当前最有价值的启发是**先完成最小流程，再按失败证据增长能力**。删掉尚未服务于首个闭环的复杂度，等真实任务证明需要时，再增加 skill、工具或执行器。
