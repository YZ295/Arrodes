## 一、会话的来龙去脉

用户（愚者）当时的状态：AI 个人管家项目分成三块 —— ①编码智能体 ②监控屏幕管家 ③桌宠（后期升级，暂无思路）。核心疑问有两个：

1. 编码智能体能不能直接用 DSH 代替？这样做出来还算不算"我的产品"？

## 二、逐轮原文（去重）

### 轮 1 · 用户
> ai个人管家现在分为三个部分：1.编码智能体。2.监控屏幕管家。3.桌宠（后期升级，但是目前没思路）。我在思考编码智能体是不是可以直接用dsh来代替，但是这样做出来的是不是不算是我的产品。虽然编码调用大模型基本确定是deepseek了

### 轮 1 · 回答（要点）
- **结论**：可以直接把 DSH 作为"编码智能体"的底层，比自造 Coding Agent 更合理。
- **关键界定**：DSH 应该是你的"编码引擎"，而不是你的"产品本身"。
- **引证**：DSH 官方定位为开放的 Agent Harness，模型/工具/Skills/会话/Sandbox/Storage/Loop/调度/UI 全部插件化可替换；MIT License，允许修改分发甚至商用（需保留版权声明）。
- **架构主张**：Butler Core（用户记忆/身份、任务理解/调度、Agent 路由、权限系统、事件系统）为产品核心；下挂 Coding Agent(→DSH→DeepSeek API)、Screen Butler(→本地视觉模型)、Desktop Pet(→UI/动画)。
- **反向警示**：如果做成"点编程 → 打开 DSH Web UI → 用户直接用 DSH"，那就只是"给 DSH 套了个壳"，会被问"你的核心工作在哪"。
- **风险提示**：DSH 截至 2026-09 仍是 **Developer Preview**，官方明说 API 与核心插件仍在变、可能出现破坏兼容的更新；官方安全说明明确 **not production-ready**，且**不能把 DSH 自带 Sandbox 当作唯一安全边界**。
- **工程建议**：不要直接大量调用 DSH 内部实现，中间加一层——
  `Butler Core → Coding Agent Interface → DSH Adapter → DSH`，
  自定义接口统一为 `create_task / send_context / start_task / pause_task / cancel_task / get_status / get_result / approve_action`，方便日后换成 Codex 或 Claude Code。
- **建议的模块重定义**：①Intelligence Runtime(DSH+DeepSeek) ②Perception(屏幕监控/活动窗口/OCR/行为识别/本地视觉模型) ③Memory&Context(用户记忆/项目上下文/Obsidian/当前任务) ④Action(Coding/Shell/文件/浏览器/PC控制/Subagents) ⑤Embodiment(桌宠/Overlay/Voice/动画)。
  —— 核心一句话：**Coding 不再与管家并列，它只是管家拥有的一种能力**。

### 轮 2 · 用户
> 这是什么意思，就是让管家去指挥dsh工作吗？

### 轮 2 · 回答（要点）
- 是，但准确说是 **AI 管家核心**当上层调度者，不是桌宠去指挥。
- 三层：`你 → AI 管家（理解你、记住你、观察你、决定该干什么）→ DSH（怎么完成编程任务）→ DeepSeek（代码推理能力）`
- 分工一句话：**管家负责"做什么"，DSH 负责"怎么把代码任务做完"。**
- 比喻：**DSH = 管家手下的程序员**，不是 DSH = 你的 AI 管家。
- 可扩展为多 Agent 路由：编码 Agent(DSH) / 浏览器 Agent / 文件 Agent。

### 轮 3 · 用户
> 但是如果我以目前的东西为架构作为插件插到dsh上面这样开发是不是更简单？

### 轮 3 · 回答（要点）—— 本会话最重要的立场翻转
- **结论**：是，"把 AI 管家做成 DSH 上的一组插件/自定义运行模式"很可能比"自造管家核心再去调用 DSH"更简单。
- **理由**：DSH 本来就是"一切皆插件"，官方甚至提供 Creator Mode 做自定义 Agent preset。自造 Butler Core 意味着迟早要解决 Agent Loop、Tool Calling、任务状态、Session、上下文管理、模型调用、多 Agent、错误恢复、插件系统、任务调度、Shell、文件系统、权限管理、日志 —— 这些与"AI 管家特色"无关但极耗时间。
- **真正的价值应该放在**："怎么让 AI 知道用户正在干什么，并主动帮助用户。"
- **屏幕监控的形态改变**：不再是独立程序，而是向 DSH 注册服务 `ScreenContextService`（`get_current_screen / get_active_window / get_recent_actions / get_selected_text / get_screen_history`），让"这个为什么报错"这类模糊指代能被自动解析。
- **"编码智能体"这一项可以删掉**，它不是并列模块而是能力。
- **桌宠不建议塞进 DSH**：透明窗口、Windows Overlay、Live2D/3D、Gaussian Avatar、鼠标穿透、系统托盘、麦克风、TTS 属于桌面 UI，用 `WebSocket/IPC` 连后台即可。后台 = DSH + Butler Plugins，前台桌宠完全自研。
- **"还算不算你的产品"**：算。类比 VS Code / Electron+Chromium+Node.js、AI 产品 / PyTorch+CUDA。决定归属的是**你自己的交互、能力组合、状态管理、屏幕感知、记忆体系、主动行为逻辑、桌宠形态**。
- **留后路**：`Butler Plugin → Butler API → DSH API`，绝不要 `Butler → 大量依赖 DSH 内部私有实现`。
- **最终定方向**："不用管家指挥 DSH，而是直接让 DSH 成为管家的 Agent Runtime/内核，围绕 DSH 开发 Screen/Memory/Context/Computer Control/Voice 插件，桌宠作为独立前端连接，编码能力直接继承 DSH。"
- **收尾自陈**：下一步真正值得设计的已经不是"要不要用 DSH"，而是**Butler Core 到底负责什么、DSH 负责什么、屏幕监控如何把上下文自动交给 Coding Agent**。

## 三、我的评估（对照本项目真实现状）

> 下面是评估，不是转述。三个判断框架：Jobs（用户真正想完成的一件事）、Linus（机制复杂度/接口稳定性/失败可诊断性/长期维护成本）、Rams（删掉只为"显得高级"的部分）。

### 1. 会话里最大的论据，在本项目上已经大打折扣

ChatGPT 劝退自造 Coding Agent 的理由是那张清单：Agent Loop、Tool Calling、任务状态、Session、上下文管理、模型调用、多 Agent、错误恢复、任务调度、Shell、文件系统、权限管理、日志。

**但这张清单，Butler 现在基本都有了**——30 秒主循环、33+ 技能、多 Agent 路由、MemoryGateway(SQLite 长记忆)、TDD(vitest+zod)、权限与副作用管控。所以"省开发量"这条论据对本项目不成立，或者说收益远小于对一个从零起步的项目。

真正的问题因此被压缩成一个更小的题：**DSH 与已有 Butler runtime，谁当内核？编码能力要不要外包？**

### 2. 引入 DSH 当内核的代价（Linus 四维）

| 维度 | 判断 |
|---|---|
| 机制复杂度 | ↑ 明显。变成两个 runtime + 一层适配，还要维护插件边界 |
| 接口稳定性 | ↓ 关键风险。DSH 是 0.1.x Developer Preview，官方明说会破坏兼容 |
| 失败可诊断性 | ↓ 除非自建 adapter 的状态/日志面，否则跨 runtime 出错难定位 |
| 长期维护成本 | ↑ 跟随上游 breaking change，且上游不是 production-ready |

再加上官方 SAFETY 明确 **sandbox 不是唯一安全边界**、不能当 production-ready 用 —— 这与本项目"本地优先 + 隐私敏感"的定位直接冲突（TTS 选型时就因为隐私/合规排除了云端方案）。

### 3. 我的建议：不换内核，只做一件小事

- **不做**：把 Butler 内核换成 DSH。现在换 = 用确定的代价换不确定的收益。
- **要做**（成本低、信息量大、且会话自己都承认这是关键）：把 Coding 抽成一层 `CodingAgentInterface`（`create_task / send_context / start_task / get_status / get_result / approve_action`），先写一个**薄 DSH adapter 做旁路试验**，内核不动。跑通后再决定要不要扩大。
- **优先级最高、且完全不依赖 DSH 的**：`ScreenContextService` 那一层。会话自己说"这一层上下文管理就是你的价值"——我同意。解决"这个为什么报错"里的"这个"，是管家区别于普通聊天框的唯一硬理由，而且它是本项目已有的本地视觉链路（MAGEVL 侧车 / 12012）的自然延伸。
- **先删**：把"编码智能体"从一级模块降级为"管家的一种能力"。这一条不需要任何外部依赖就能做，且能立刻简化架构叙事。
- **按既有纪律**：这属于"加新功能 vs 补验证债"里的后者优先档 —— 在动内核之前，先补屏幕感知这条链路的端到端验证。

### 4. 一句话总结

会话给的方向（DSH 当编码引擎）在**取舍上是合理的**，但它的论证前提（"你要自造轮子"）对 Arrodes/Butler 不成立；而它自己指出的"下一步"——**划清 Butler Core 与 Coding 的边界、把屏幕上下文自动喂给 Coding**——才是这个项目真正该做的一步，且这一步今天就能做，不必等 DSH。

## 四、追问：把 DSH 改造成管家后，它到底是 DSH 还是阿罗德斯？

### 1. 归属由三件事决定，不由代码血缘决定

| 判据 | 落在你手里 → 产品是你 | 落在 DSH 手里 → 你只是皮肤 |
|---|---|---|
| **入口** | 用户双击的是你的 exe，桌宠长的是你的脸 | 用户看到 DSH 的 TUI / Web UI |
| **状态** | 记忆、习惯、项目上下文、宠物形象存你自己的库 | 塞进 DSH 的 storage 插件，DSH 一炸你就归零 |
| **可见性** | 用户终身见不到 DSH 的界面、术语、配置 | 用户要自己配 DSH 的 provider / 插件 |

三条全在你这儿 → 产品是阿罗德斯，DSH 是基础设施。任一条落在 DSH 里 → 你确实在做 DSH 的皮肤。

### 2. 最强类比：Cursor 与 VS Code

Cursor 就是 fork 出来的 VS Code。**没有人说"Cursor 就是 VS Code"。** 因为它做了三件事：重写交互（Tab / Cmd-K / Composer）、自建状态（代码库索引、规则、模型路由）、独立品牌与分发。

反例：`dsh` 换个 logo + 加一个桌宠启动按钮 = 你确实就是 DSH。

### 3. 一个可检验的判据：替换成本测试

> 明天把 DSH 换成 Codex 或自研 runtime，需要改多少代码？

- **< 10%** → 是你的产品
- **> 50%** → 是 DSH 的产品

这条比任何主观感受都硬，也是唯一能正面回答"你的核心工作在哪"的证据。

### 4. 但"现行 Butler 不成熟" ≠ "应该换成 DSH"

先把"不成熟"拆成两层，这两层的解药完全不同：

| 层 | 内容 | DSH 能补吗 |
|---|---|---|
| **骨架层** | 主循环、调度、插件注册、权限、Session | **能** |
| **能力层** | 33 个技能的实现深度、记忆检索准确率、路由命中率、屏幕感知质量 | **不能** |

换骨架**不会**让 33 个技能变好用，也不会让记忆变准。如果不清点就换，大概率得到：一个更新更漂亮的骨架 + 同样不成熟的技能 + 一个会破坏兼容的上游。

**建议动作**：先花半天清点——33 个技能里真正能用的是几个？主循环的毛病是架构问题还是实现问题？这一步做完，换不换的答案会自己浮出来。

### 5. 阿罗德斯其实已经握住了最硬的三张牌

- **身体**：桌宠（EmotionBall / VRM 备选）
- **眼睛**：本地视觉链路（MAGEVL 侧车 12012）
- **记忆**：SQLite 长记忆 + MemoryGateway

DSH 提供的是**没有身体、没有眼睛的智能骨架**。谁有身体和眼睛，谁就是产品。

### 6. 如果结论确实是"换"

那就把线一次画死：

```text
保留在阿罗德斯          交给 DSH
─────────────────      ─────────────────
用户状态                Agent Loop
交互契约                工具系统
桌宠 / 身体             Session
记忆库                  Sandbox
本地视觉链路            Scheduling
品牌与分发              Coding 能力
```

并且**必须先做那个适配接口**——它不只是为了将来可替换，它本身就是"这是你的产品"的证据。

### 7. 代价（必须交代）

走这条路要牺牲：短期可控性（DSH 0.1.x 会变）、上游稳定性预期、以及"完全自研"的讲述资格。换来的是：把开发时间从"造骨架"挪到"造身体、眼睛、记忆"。

**这笔账是划算的——前提是先做完第 4 步的清点，而不是因为"现有东西不成熟"就直接推倒。**

## 五、代码取证：用户提出的四个理由，逐条对账（2026-09-12 追加）

用户给出的换 DSH 的理由：①每次要开前端还要开后端、命令不熟、桌面放个 cmd 不好看 ②换成 DSH 它就能自己改自己 ③阿罗德斯连删个软件都删不干净，操作电脑能力弱 ④后续要可迭代，DSH 有插件市场；「我加的眼睛/记忆/skill 都是我的，所以做出来的不是 DSH」。

在仓库里逐条查证，结论跟上一节的推断**有出入**，以下以代码为准。

### 发现 1：这个项目已经是一个 mini-DSH 了（2026-08-14 起）

`spec/deepseek-harness-integration.md` 记录了把 DSH 第一性原理移植进阿罗德斯的落地，已完成项：

- **一切皆插件 / 能力即 seam / 事件即扩展点 / 注册即副作用 / 模型可见⟺已记录**（五条原理逐条对应）
- `server/src/skills/registry.ts`：`ToolPreHook` / `ToolPostHook`，`executeToolCall` 按 `pre → execute → post` 执行，注册返回 disposer
- `actionGate` 从技能内部抽离，成为默认 pre 钩子；技能只声明 `risk` / `describe`，提供纯 `execute`
- `server/src/harness/harness.ts`：`on` / `emit`（返回 disposer），发出 `turn:start` / `turn:end` / `turn:error`
- fs（`fsProvider.ts`）/ subprocess（`commandProvider.ts`）/ llm（`llmProvider.ts`）三条 seam 已抽象为 Definition / Provider / Consumer 三角
- `services/skillProfile.ts`：按配置启用/禁用技能（轻量版 profiles / bundles）

**结论**：换 DSH 不是从 0 到 1，而是**用别人的实现替换你已经有的同构实现**。这也解释了为什么 DSH 的概念对你毫无陌生感——两个月前你就照着做了。

### 发现 2：「删软件删不干净」的直接病因是黑名单，不是能力弱

`services/computerService.ts` 的电脑操控总共只有 4 个原语：`exec_command` / `read_file` / `write_file` / `list_dir`。
而卸载软件所需的几乎每一条命令都在 `BLOCKED_PATTERNS` 里：

| 卸载步骤 | 需要的命令 | 状态 |
|---|---|---|
| 跑官方卸载器 | `winget uninstall` / `uninstall.exe` | 可通过 |
| 删残留目录 | `rmdir /s`、`del /s`、`del /f` | **被拦截** |
| 删注册表项 | `reg delete` | **被拦截** |
| 删/停服务 | `sc delete`、`net stop` | **被拦截** |
| 强杀残留进程 | `taskkill /f /im` | **被拦截** |

源码注释写得很明白：「危险命令黑名单拦截（**宁可多拦，不可漏网**）」。

**所以"删不干净"不是模型不行，是你自己按设计拦的。** 而且换 DSH 也不会好——DSH 同样只给你一个 shell，权限策略还是得你自己写，且官方明确说它的 sandbox 不是唯一安全边界。真正要改的是：把"卸载软件"从"让模型拿 shell 自由发挥"升级为**一个有固定流程、有确认、有报告的高危技能**，由技能自己申请所需权限，而不是让模型临时拼命令去撞黑名单。

### 发现 3：「自己改自己」你已经在做了，缺的是安全网不是引擎

`skills/selfModify.ts` 已存在：`self_modify` 技能把改动任务委派给本机 codex CLI
（`codex exec --ephemeral -C <repoRoot> -s <sandbox> --color never -o <outFile>`，15 分钟超时）。

但三个缺口：
- 沙箱默认 `danger-full-access`（注释：本机 Windows 沙箱起不来时兜底）
- **没有 git 回滚** —— 改坏了没法一键撤销
- **只返回文本摘要**，没有"改完还能不能启动"的验证

所以"自我迭代"不是新能力，是把已有雏形补成可靠能力。补三样：每步一提交、一条命令回滚、改完必须跑 smoke test 才算成功。

### 逐条对账

| 你的理由 | 换 DSH 能解决吗 | 真实病因 | 该做什么 |
|---|---|---|---|
| ① 要开前后端、命令不熟、cmd 不好看 | **不能**（与架构无关） | 启动编排问题 | 一个静默启动脚本拉齐所有进程，半小时的事 |
| ② 换 DSH 就能自己改自己 | 部分（引擎早有了） | 已有 `self_modify`，缺回滚 + 验证 | 补安全网，不用换引擎 |
| ③ 删软件删不干净 | **不能** | 自己的黑名单拦掉了卸载必需的 4 类命令 | 写"卸载软件"技能：流程化 + 申请权限 |
| ④ 要可迭代、有插件市场 | **能** | **唯一真正需要 DSH 的一条** | 用最小实验验证插件链路 |

**四个理由里只有 ④ 真的指向 DSH。** ①②③ 都能在现有代码里直接改掉，而且 ③ 的确切位置已经找到。

### 关于「做出来的不是 DSH」

**用户说得对**，而且他的判据比我上一节那套更简洁：*我加的眼睛、记忆、skill 都是我的 → 所以产品是我的*。这就是"替换成本测试"的直觉版本。

唯一要补的前提：**加的东西必须长在你自己的数据里。** 记忆写进 SQLite / 自己的文件，眼睛走自己的本地视觉链路——不要写进 DSH 的 storage 插件。否则 DSH 哪天破坏兼容，记忆和眼睛一起陪葬。

### 插件市场的双刃剑

- 好的一面：眼睛、记忆、PC 控制大概率有现成的，省事。
- 风险一面：DSH 还在 0.1.x，插件同样在变；且第三方插件是**别人写的代码，跑在你机器上，带文件 / 进程 / 网络权限**——对一个"本地优先 + 隐私敏感"的项目（曾因隐私合规砍掉云端 TTS）这是新增攻击面。装之前必须能看清它要什么权限。

### 修正后的建议（覆盖第二节的排序）

上一节说"不换内核"，排序需要调整。更准确的三条：

1. **别把 ①②③ 算进"换架构的收益"里。** 它们与架构无关，今天就能修，且 ③ 的确切位置已经找到——继续拿它们当换 DSH 的理由，会高估收益。
2. **先花两天做最小可证伪实验**：写一个 DSH 插件，只注册一个能力（例如 `get_active_window`，即"眼睛"的最小版本），跑通「我的代码以插件形式被 DSH 加载并调用」这一条链路。通了 → 眼睛/记忆/skill 都能往上堆；不通（插件 API 太烂 / 装不起来）→ 现在就知道，损失两天而不是两个月。
3. **同时把 `self_modify` 补上安全网**（git 每步提交 + 一条命令回滚 + 改完跑 smoke test）。这件事**不管最后换不换都要做**，而且它是"能不能把它自己能改自己这件事托付出去"的前提。

## 六、结论修正：DSH 是宿主，不是编码智能体（2026-09-12 当晚）

用户指出上面几节的理解有偏差，并给出更准确的重述：

> DSH 有编码能力，但在我这里不主要作为编码智能体。……我做的三块东西后期还要合并，不如先合并到 DSH；DSH 只是作为一个壳，真正的灵魂不在 skill（这些网上都有，想怎么装怎么装），**灵魂在管家**。我把灵魂塞进了 DSH 的身体里，方便我进行管理，仅此而已。

### 我上一轮抓错了重点

我一直在论证"你的能力不弱，所以不必换"，把 DSH 当成**编码智能体**来评估。
但用户的诉求不是能力，是**宿主 / 容器** —— 要一个统一的身体把现在分散的东西装进去，好管理。

同一个东西换个角色，评估标准完全不同：

| 把 DSH 当作 | 比较什么 | 本项目结论 |
|---|---|---|
| 编码智能体 | 谁写代码更强 | 已有能力，**别换**（第二、五节的结论） |
| **宿主 / 容器** | 能不能把三块东西装进一个生命周期统一管理 | **值得换**（本节的结论） |

### 这个诉求成立，而且顺带解决了一条技术债

工作记忆里记着：`Agent/` 与 `Butler/` 是两套独立副本，**本来同属一个项目，因开发程度大暂未合并**，计划后期合并回 Agent。

用户的思路是：**不合并两套代码，而是把它们都变成插件。** 这比合并两个 Node 项目更聪明 —— 插件边界天然就是模块边界，"合并"退化成"决定哪些插件保留"。三块东西（编码 / 屏幕管家 / 桌宠）也从"三个程序"退化成"一组插件"。

### 但要落两条硬约束，否则灵魂会被身体吃掉

**约束 A：灵魂必须可搬运。**
先把"灵魂"定义清楚，否则搬家时不知道搬什么。建议的最小定义：

| 灵魂（必须住在你自己那里） | 身体（DSH 提供，可换） |
|---|---|
| 长记忆（SQLite + MemoryGateway） | 插件加载 |
| 用户状态 / 配置 | 生命周期 |
| 人格与提示词 | 调度 |
| 路由决策 | 会话 |
| 桌宠形象与形态 | 工具执行管线 |
| 本地视觉链路（侧车 12012） | 编码能力（顺带） |

判定方法仍然是那句：**把 DSH 整个换掉，灵魂需不需要重写？** 不需要 → 灵魂是你的。

**约束 B：先验证身体挂得住。**
实验目标要改。原来建议的 `get_active_window` 是在验证"DSH 能不能当编码智能体"，方向错了。
应改成：**把一个真实的灵魂零件挂上去** —— 首选**记忆**。因为记忆是灵魂核心，数据天然在你自己库里，一次实验同时验证「宿主能挂」和「灵魂能在外面」。

### 一句必须说的实话：收益要落在对的那一侧

"方便管理"有两种，价值差很远：

- **少开几个窗口** → 半小时的启动脚本就能解决，**不值得为它换架构**
- **一套宿主管住所有能力** → 结构性的，**值得为它换**

用户要的是后者。理由要明确落在后者上，否则将来会发现管理面并没变小 —— 只是从"开两个进程"变成"装插件、配插件、处理插件冲突、跟上游破坏兼容"。

### 修正后的建议

1. **方向认可**：DSH 当宿主、灵魂自己留着，这条路成立，且顺带吸收 Agent/Butler 的合并债。
2. **先做定义（半天）**：把"灵魂"落成一张清单 —— 哪些数据、哪些代码、存在哪个目录 / 哪个 DB。这是后面一切的前提。
3. **再做实验（两天）**：把「记忆」做成一个 DSH 插件挂上去，数据仍在自己的 SQLite。通了 → 眼睛、路由、桌宠依次上；不通 → 损失两天。
4. **同时**：给 `self_modify` 补安全网（git 每步提交 + 回滚 + smoke test）。这条不管换不换都要做。

## 七、两个收尾问题：算不算我的项目 / 要不要克隆源码（2026-09-12）

### Q1「这样真的算我的开发吗？只是加几个插件罢了」

这是第六节"灵魂塞进身体"这个比喻自己带出来的问题，**而且问得对 —— 只加插件确实不够。**

判据（比"用户看到谁"更硬）：**看最后跑起来的那个「循环」是谁的。**

`server/src/services/mainloop.ts` 的 30 秒主循环是现成资产，也是这个项目的**心跳**。心跳决定归属：

- DSH 的 loop 在跑，你的插件只是器官 → 产出是一袋插件，别人装同样的插件会得到同样的东西
- 你的主循环在跑，DSH 只当手 → 产品是你的

**关键好消息**：官方 README 确认 DSH 是 everything-is-a-plugin，且**调度（Scheduling）本身就是可替换插件**。所以"把自己的 30 秒心跳装进去"是 DSH 设计的正常用法，不是 hack。

| 层级 | 谁在跑心跳 | 产出 |
|---|---|---|
| ① 只加插件 | DSH 的 loop | 一袋插件 |
| ② **换掉心跳（推荐）** | 你的 30 秒主循环 | 你的管家 |
| ③ 改宿主内核 | fork 的 Cordis | DSH 的一个分支 |

**修正第六节的比喻**：灵魂不是"几个插件"，灵魂是**那个在驱动的心跳**。插件是器官（可以从外面买），循环是心跳（必须是你自己的）。

### Q2「需不需要把 DSH 源码克隆到电脑上」

官方 README（`raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/README.md`）确认两条路径：

```sh
# 路径 A：不克隆，直接跑
npx @deepseek-ai/dsh web        # 默认起 Web UI 于 http://127.0.0.1:3080

# 路径 B：从源码跑
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness && pnpm install && pnpm run build && pnpm dsh web
```

按层级决定：

| 你想做什么 | 要不要克隆 |
|---|---|
| 只是想跑起来看看 | **不用**（路径 A 即可） |
| 搞懂插件 / 调度怎么插（层级 ②） | **先读文档**：repo 内有 `docs/architecture.md`、`docs/development.md`，GitHub 上直接看，零成本 |
| 文档讲不清、要读内核实现 | **浅克隆**（C 盘紧张，放 E 盘） |
| 要 fork 改宿主（层级 ③） | 必须克隆，但建议先别走到这步 |

浅克隆（只读代码，不装依赖，体积小很多）：

```sh
git clone --depth 1 https://github.com/deepseek-ai/deepseek-harness.git E:/AI/deepseek-harness
```

**克隆了先别 `pnpm install`** —— 那是为了跑起来，不是读代码。读结构浅克隆就够。
官方文档站：https://deepseek-harness.github.io/deepseek-harness/

### 一条建议写进项目纪律的提醒

DSH 默认的脸是 **Web UI（127.0.0.1:3080）**。一旦你的管家 = 那个页面，第六节"用户看到的是谁"就真的出问题了。
**DSH 必须跑在后台，用户永远见不到那个页面，只见到桌宠。** 这条建议提为纪律候选（尚未经用户确认）。
