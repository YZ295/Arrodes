# 悬浮语音管家前端 · 形态需求文档 v1.1

> 2026-09-10 · 苏格拉底式五问收敛产出 · 需求来源：胤玮
> v1.1（同日）：并入 Terse-AI/terseai 调研结论，M0 视觉线修订为「EmotionBall + 粒子光环」
> 关联调研：livekit/agents（GitHub main 分支 + docs.livekit.io，2026-09 活跃开发中）

## 0. 一句话定位

**桌面上一个静默在场、有表情和目光的活物；你随时直接开口，它听懂并开口回答，说完回到安静。**

身份：**在场陪伴**。
- 不是观察员——不主动搭话、不推送提醒（主动性被明确排除）
- 不是工具面板——不弹对话窗、不占工作区（点击展开方案被排除）
- 不是装饰桌宠——有真实语音对话能力（纯氛围球被排除）

## 1. 交互节奏（状态机）

```
┌─────────┐   直接开口    ┌─────────┐   对话结束    ┌─────────┐
│  在场态  │ ──────────→ │ 对话中   │ ──────────→ │ 回归在场 │
│静默·表情·目光│  always-on │ 语音回合  │  无话30s    │ 表情回落 │
└─────────┘   监听      └─────────┘  (可点击打断)  └─────────┘
```

| 状态 | 视觉 | 听觉 | 进入/退出触发 |
|------|------|------|--------------|
| 在场 | 目光跟随光标/窗口，表情随场景微变 | 麦克风开着但零输出 | 默认态；无话 30s 退出对话 |
| 对话中 | 表情切"倾听/思考/回复"三态 | 语音进+语音出 | 用户开口（VAD）；点击打断退出回合 |

核心反差即产品性格：**嘴巴基本闭着（静默在场），耳朵永远开着（随时可叫）**。

## 2. 五个已收敛决策

| # | 问题 | 决策 | 被排除的选项 |
|---|------|------|-------------|
| 1 | 核心时刻/身份 | 在场陪伴 | 动口不动手工具 / 唤起即用面板 / 常驻观察者 |
| 2 | 在场感来源 | 活的表情 + 目光跟随 | 低频主动开口 / 纯呼吸动画 |
| 3 | 对话过渡 | 直接开口（always-on） | 按键说话 / 点击展开 / 维持现状 |
| 4 | 形态路线 | 先小球后进化（M0→M1） | 直接上拟人 / 小球永续不进化 |
| 5 | 球体操作面 | 拖动 + 单击静音 + 点击打断 | 戳一戳彩蛋（砍）；其余收编托盘/菜单 |

## 3. M0 形态规格：EmotionBall 2.0

**球体表面只保留三个物理交互：**
1. **拖动定位**——位置刚需
2. **单击静音/恢复**——对 always-on 麦克风的物理安全感开关（含可见的状态指示：表情或光环变化）
3. **点击打断**——它说话时点一下立即停（语音 barge-in 的可靠兜底）

**收编进托盘/右键菜单**（功能不删，离开球体表面）：透明度滑条、形象切换、机位设置、聊天历史窗、退出。

**表情/目光强化（现有资产上的增量）：**
- 目光跟随：EmotionBall `setGaze` 已有基础 → 升级为跟随光标 + 活动窗口方向
- 表情状态机：现有状态→表情映射扩展对话三态（倾听/思考/回复），由语音会话事件驱动（见 §4）

**M1 升级触发条件**（出现任一信号才值得投入美术资产，避免拍脑袋进化）：
- 你持续因"目光/情绪读不出来"而不满——球体的注视语义到了天花板
- 出现"管家需要身份形象"的新需求（如对外展示、拟人化叙事）
- 连续多次想表达的表情状态在球体上做不出来
- **反向判据**：若 2-4 周日常使用中从未因表情受限而困扰 → 小球即终态，省下全部美术成本

## 3.5 视觉升级修订（v1.1）：EmotionBall + 粒子光环

**terseai 调研结论**（Terse-AI/terseai，2026-09）：
- 项目本质是 **AI 编码代理成本管家**（token 监控/提示词压缩 40-70%/预算熔断 SIGSTOP），**无任何语音组件、无虚拟形象**——对语音链路零输入
- 视觉资产 = 原生 WebGL 粒子壁纸引擎：官网 `terse-field.js`（~1800 行，自包含 IIFE，零依赖：BED 星系底/FIELD 粒子场/CITY 代码天际线/GLYPH 粒子文字，10 种编舞 + 9 种散开动效，30fps 限流 + visibilitychange 暂停 + prefers-reduced-motion 降级）
- **法律红线**：该文件在官网而非 MIT 仓库内、无许可证头；桌面壁纸引擎本体闭源（$4.99/月 app）→ **只能学技法自研，不可 vendor**（区别于 NX_emotion-ball 的双许可引用）
- **GPU 现实**：官网全开 24 万+粒子全屏，4060 上与 qwen3-vl（4GB）冲突；但小球级视口（1-3k 粒子 + 30fps + 页面隐藏即暂停）成本极低，terse 自身的降级设计证明该路径成立

**拍板（用户选定）**：M0 视觉 = **保留 EmotionBall 球体与状态映射**，外圈新增**数据驱动粒子光环层**（terse PULSE 思路的自研小视口实现）：
- 思考中 = 粒子脉动；说话 = 涟漪扩散；静音 = 呼吸减慢；屏幕观察 = 微光；错误 = 红色闪烁
- 实现约束：raw WebGL 1 自研（不引 three.js）、单一 canvas 置于球体后、事件驱动（复用 eventBus）、30fps 封顶、`visibilitychange` 暂停、`prefers-reduced-motion` 回退纯球体
- 桌面壁纸形态（terse 本体方向）被否决——与"悬浮前端"定位冲突（壁纸在桌面层，管家在顶层）
- Terse SDK 本体（MIT，token 压缩/代理成本监控）与前端形态无关，记录为管家功能 backlog：管家可扩展"编码代理成本监控+熔断"能力

## 4. 语音链路 → livekit/agents 映射（结合点）

**调研结论**：Python 框架，Apache-2.0（注意：turn detection 模型为 LiveKit Model License，本地使用免费、再分发需看条款）；核心架构 = AgentServer（进程编排）+ AgentSession（语音管线）+ Agent（人设/工具）；Node.js 有 AgentsJS 并行实现。**无官方本地 STT/TTS 插件，但插件框架明确支持自定义与本地推理。**

| 需求 | livekit 能力 | 接入方式 | 缺口/备注 |
|------|-------------|---------|-----------|
| always-on 监听 | 内置 silero VAD | 原生 | **唤醒词无内置** → openWakeWord（Apache-2.0）本地外挂；M0 可先用 VAD+静音键顶 |
| 回合判断（说完没有） | 语义 turn detection（transformer 模型） | 原生插件 | 减少"话没说完就被接嘴" |
| 打断（barge-in） | 内置 interruption 处理 | 原生 | 物理点击打断 → 映射 `session.interrupt()` |
| STT 本地 | 无官方本地插件 | **faster-whisper 自包装**（int8 CPU 跑，不挤 4060 显存） | 云端 STT 违背隐私叙事 → 否决；中文质量后续可换 FunASR/Paraformer |
| TTS 本地 | 无官方本地插件 | **灵语 sidecar 包成自定义 TTS 插件**（StreamAdapter 适配整段返回，后续可流式化） | 保留已拍板的灵语 1.25x 音色 |
| LLM | openai-compatible base_url 直连 | M0：Ollama 直连最短路径；M1：桥接现有 server 主 agent（复用人设+技能+记忆） | 桥接是新工程，M0 不做 |
| 表情驱动 | session 事件（user/agent speaking 状态机） | 经 EventBus → EmotionBall 状态映射 | 需写事件桥 |
| 多端未来 | WebRTC 客户端生态（手机/浏览器连同一 agent） | 天然支持 | 当前用不上，但是"选 livekit 而非裸 WS"的真实理由之一 |

## 5. 部署拓扑（本机全离线）

```
Electron 桌宠窗口 ──WebRTC(loopback)── LiveKit Server ─── Agent Worker (Python)
   livekit-client                    自托管·新端口        =第三个sidecar
   (EmotionBall 2.0)                 (待端口登记)         VAD+turn-det+whisper+灵语+Ollama
```

- LiveKit Cloud 被否决（音频上云 = 复刻云端 TTS 的隐私错误），**自托管 loopback，音频全程不出机器**
- Agent worker 复用现有 sidecar 模式（tts-sidecar / vision-sidecar 之后的第三个），符合 Butler 架构惯例
- 新增端口需按 Butler 端口纪律登记进文档与 .env（LiveKit 默认 7880）

## 6. 牺牲了什么（代价清单）

1. **两个新常驻进程**（LiveKit server + agent worker），内存与启动开销
2. **本地 STT 质量低于云端**——whisper 本地中文可用但非顶级
3. **架构超配风险**——单机单用户跑 WebRTC 全家桶是超配；换来的是语义回合检测 + 打断体验 + 未来多端。若 M0 验证发现 90% 场景只是"一问一答"，**裸 VAD+WS 轻量路径保留为合法降级选项**
4. turn detection 模型许可非 Apache——自用无碍，开源分发时需单独声明

## 7. M0 验收清单

- [ ] 单击球体 → 静音态可见（表情/光环变化），VAD 停止采集
- [ ] 直接开口说话 → 1.5s 内开始回应（首包目标）
- [ ] 它说话时点击球体 → <200ms 停止
- [ ] GPU 占用：qwen3-vl（4GB）不被语音链路挤掉（whisper 走 CPU int8）
- [ ] 对话结束 30s 无话 → 自动回归在场态表情
- [ ] 音频不出本机（进程网络连接仅 loopback 验证）
- [ ] 粒子光环：30fps 封顶、页签隐藏即暂停、reduced-motion 回退纯球体；桌宠进程 GPU 增量不影响 qwen3-vl
